# TASK-098 总格数性能安全边界评估

日期：2026-10-12

## 产品边界

按 PRD §6.1 及 2026-10-12 产品确认，V1 不增加 Grid 总格数性能警告，也不增加人为总格数硬上限；用户可设置宽度仍为 8～256。总格数只受安全整数校验、既有合法宽度及实际浏览器资源条件约束。本文中的风险区间和建议是工程观察，不是产品限制。现有上传图片提示、极端比例提示和 PDF 单格可读性警告保持不变。

## 测量环境与样本

- 环境：Windows 10 x64，Headless Chromium 151.0.7922.34，`navigator.hardwareConcurrency=12`。
- 测试通过真实上传、Crop、真实 Worker generation、自动保存及页面刷新恢复；使用确定性的 64×320 实色 PNG，最终宽度 256、派生高度 1,280。
- Grid 为 327,680 格，正式 `Uint16Array` 长度 327,680、数据 655,360 B（625 KiB）。刷新后完整摘要与 Grid hash 一致；E2E 没有出现新增总格数提示，仅保留既有极端比例提示。
- 从点击生成到 Editor/Grid 可用：1,399.74 ms；刷新开始到恢复后的 Editor/Grid 可见：338.62 ms。均为该自动化环境一次观测，不是算法耗时或设备保证。
- 单元测试还验证 256×1,280 Grid 可创建并被 Export Snapshot 精确复制；超出安全整数范围的输入仍由既有整数/尺寸校验拒绝，不添加“实用格数阈值”。

## 风险区间（工程观察，不是 UI 告警）

1. **本批直接验证范围：** 256×192（49,152 格）已覆盖真实 PNG、自动/手动 PDF 导出、精确分页覆盖；256×1,280（327,680 格）已覆盖真实 Worker 生成、IndexedDB 自动保存和刷新恢复。仅代表上述浏览器和机器环境。
2. **高成本工程区间：** 从 256×1,280 起，当前单 Grid 仍小于 1 MiB，但完整 50 条 History 的 before/after 数组按设计约 62.5 MiB；Canvas、PDF、Blob、解码器、Worker 和浏览器原生资源会叠加，且本批未测高宽比大 Grid 的 PNG/PDF。因此需要目标设备压力与进程内存测量。
3. **未验证范围：** 大于 327,680 格、重复高频编辑形成完整大 Grid History、极端比例 Grid 的完整导出以及低内存设备/浏览器行为均未测得。不能据此推断能成功或失败，也不据此禁止用户操作。

## 内存观测限制与安全行为

浏览器测试环境没有可靠的进程峰值 RSS/原生内存采集能力。`performance.memory.usedJSHeapSize` 不覆盖 Canvas/GPU、图片解码器和浏览器进程其他分配，故不使用它冒充峰值内存。报告中的 typed-array/history/canvas 数字是精确长度或容量公式，不是进程峰值。

已有失败保护保持：Worker generation 失败不提交新 Grid；IndexedDB 写入失败保留当前内存 Project 和上一份有效保存快照，并提供重试；Canvas/PNG/PDF 失败走现有错误提示，不清除 Project/Grid。没有新增自动降格、自动删数据或新产品限制。

## 后续工程建议

- 后续优化应先在目标低配设备采集浏览器进程 RSS、原生图像/Canvas 内存和重复编辑压力；不要将 JS heap 作为替代指标。
- 若实际资源失败可复现，优先评估按可见范围渲染、History 快照压缩/结构共享、可取消导出和阶段性释放临时 Canvas，并验证历史语义与正式图纸信息不变。
- 可把更大 Grid PNG/PDF、低内存设备及长时间编辑纳入未来性能测试矩阵；只有经过产品决策才可以改变 V1 用户可见规则。
