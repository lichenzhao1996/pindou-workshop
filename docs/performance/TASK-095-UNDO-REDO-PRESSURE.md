# TASK-095 Undo / Redo 快照压力记录

日期：2026-10-12

## 可重复条件与结果

- 定向单测：`tests/unit/task095.history-pressure.test.ts`。
- 采用 52 次有变化的单格编辑，覆盖 8×6、64×48 和 256×192 Grid；校验 `MAX_GRID_HISTORY_ENTRIES=50`、当前 Grid 保留、快照恢复及 Undo/Redo 往返。
- 真实 Chromium E2E：在 256×192 作品上进行一条跨 5 格的画笔手势，再执行 Undo / Redo 并逐格比较完整 Grid。
- 真实 E2E 单次操作观测：画笔约 390.39 ms、Undo 约 324.04 ms、Redo 约 324.17 ms。计时包含浏览器输入、状态更新和测试轮询，不等同于纯历史函数耗时。

## 可精确计算的 Grid backing-store 内存

当前 `GridHistoryEntry` 为一次操作保留 detached before/after 两个完整 `Uint16Array`；50 条历史因此保留 100 个 Grid 数组。下表仅统计这些历史数组的精确字节数，不包含当前 Project Grid、对象/操作元数据、Canvas、Blob、浏览器解码器或临时分配。

| Grid    |          单个 Grid | 50 条历史数组（before + after） |
| ------- | -----------------: | ------------------------------: |
| 8×6     |               96 B |          9,600 B（约 9.38 KiB） |
| 64×48   |   6,144 B（6 KiB） |            614,400 B（600 KiB） |
| 256×192 | 98,304 B（96 KiB） |        9,830,400 B（9.375 MiB） |

作对照，256×1,024 时同一 50 条上限的历史数组约 50 MiB；256×2,048 时约 100 MiB。高度由裁剪比例派生，当前没有总格数产品硬上限。因此这些是按正式全快照实现计算的工程风险，不是 PRD 限制，也不是实际进程峰值内存测量。

## 保护与结论

- 项目保留现有 50 条工程上限；第 51 条及后续操作会淘汰更旧的历史项，不改变当前 Project/Grid，也不静默丢失当前编辑结果。
- 画笔按一次 pointer 手势合并成一条历史；5 格 E2E 手势只产生一条记录。
- 单测通过 52 次编辑后确认历史仍为 50 条，最新 Grid 仍可 Undo/Redo，且恢复后的 `Uint16Array` 内容正确。
- 本 headless 环境无法可靠采集浏览器进程峰值内存，未用 JS heap 数值冒充 RSS。
- 建议 TASK-098 用总格数压力结果审阅极端高宽比下的历史留存建议；本任务没有自行改变历史条数承诺或新增总格数限制。
